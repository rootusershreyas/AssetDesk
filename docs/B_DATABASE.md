# B: database setup and team handoff

The database belongs to the AssetDesk prototype. It uses its own Compose project,
database and volume. The development PostgreSQL port is `127.0.0.1:5434`; the API
runs at `127.0.0.1:3000` by default.

## Start from a fresh checkout

Create a local environment file if one does not already exist:

```bash
cp .env.example .env
docker compose up -d --wait db
docker compose ps
```

The example contains development credentials for this Compose database. `.env` is
ignored; `.env.example` is committed. A PostgreSQL health check confirms that the
server is accepting connections. The named volume preserves local data when the
container stops.

Start the API:

```bash
cargo run --locked
```

Startup loads `.env`, connects through the SQLx pool and applies the committed
migrations before serving HTTP. An application or migration failure prevents the
server from starting.

Verify connectivity and schema:

```bash
xh GET http://127.0.0.1:3000/ready
docker compose exec db psql -U assetdesk -d assetdesk -c '\dt'
```

The schema contains `employees`, `assets`, `assignments`, and SQLx's migration
tracking table. `/health` checks the process; `/ready` checks an actual database
query with a timeout. Database readiness is separate from HTTP process liveness.

Stop the development database when finished:

```bash
docker compose stop db
```

## Migrations

`migrations/202611120001_create_assetdesk_schema.sql` is the shared baseline.
It creates all three agreed tables so A, B and C can work against the same schema.
UUIDs are generated by Rust, and timestamps are stored with time zones.

The baseline enforces:

- Lowercase, trimmed, unique employee emails and valid employee statuses.
- Uppercase, trimmed, unique asset tags and valid operational statuses.
- Required employee/asset references with deletion restrictions.
- Valid issue/return conditions and positive assignment versions.
- Expected return after issue, and actual return at or after issue.
- Return timestamp and return condition being absent or present together.
- One outstanding assignment per asset using the
  `one_open_assignment_per_asset` partial unique index.

History indexes support employee and asset assignment collections. Availability
and equipment clearance are calculated from assignments; neither has a separate
stored boolean.

SQLx remembers applied migrations. After the baseline has been shared and
applied, add a new migration for schema changes instead of editing the baseline.
The application applies migrations, so SQLx CLI is optional. If already installed,
it can also apply them from the repository root:

```bash
"$HOME/.cargo/bin/sqlx" migrate run
```

The CLI reads `.env`. Keep the crate and CLI on compatible SQLx versions when
using it. There is no need to run `sqlx database create`: the Compose PostgreSQL
service creates the development database on its first start.

## Tests and CI

Integration tests use `#[sqlx::test(migrations = "./migrations")]`. Each database
test gets an isolated database with the real migration applied. The local
development role can create these databases; the Compose role has that capability
because it initializes this dedicated PostgreSQL instance.

Run the same checks as CI:

```bash
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
DATABASE_URL=postgres://assetdesk:assetdesk_dev@127.0.0.1:5434/assetdesk cargo test --locked
```

Database tests must fail if PostgreSQL is unavailable, rather than silently skip.
Keep this test URL pointed at the dedicated development/test server. The GitHub
Actions workflow provides its own PostgreSQL 17 service and uses the same
migrations; its database port is `5432`, while local Compose uses `5434`.

The workflow runs for feature pushes and pull requests into `develop` or `main`.
It does not merge branches or change repository protection settings.

## Transaction contract for A and C

Use the same lock order for operations needing multiple rows:

```text
employee -> asset -> assignment
```

**Issue (C):** begin a transaction, lock the employee and then asset with
`SELECT ... FOR UPDATE`, validate the employee is active and the asset is in
service, check for an outstanding assignment, insert the assignment, and commit.
Map an `one_open_assignment_per_asset` violation to HTTP `409 Conflict` as a final
guard against duplicate custody.

**Employee status update (A):** lock/update the employee row in the transaction.
This serializes against issue requests. Deactivation is allowed while equipment
is outstanding; it prevents new issues but does not prevent returns.

**Asset status update (B):** lock the asset row before inspecting outstanding
assignments. Reject maintenance/retired while the asset is assigned. Make the
validation and metadata update one transaction so a rejected status change
cannot partially update other asset fields.

**Return (C):** read the assignment's immutable employee/asset IDs, then lock the
employee, asset and assignment in that order. Recheck the assignment is
outstanding and the supplied version is current. Record the return timestamp,
condition and incremented version together. A damaged return also moves the asset
to maintenance in that transaction. Return to an inactive employee is permitted.

An expected return timestamp is a deadline. It does not automatically release
custody. Leave assignment employee/asset IDs immutable and retain returned records.

The migration enforces row-local constraints and exclusive outstanding custody.
The application transaction rules enforce cross-table state rules; a plain
foreign key cannot check whether an employee is active or an asset is in service.
